Claude Cockpit

Dashboard personal para orquestar agentes Claude Code CLI. Define proyectos, configura agentes con sus skills y lanza tareas que se ejecutan de forma autónoma sobre tus repos locales.

Fastify 5 Next.js 15 Prisma + SQLite claude CLI SSE streaming single-user local

¿Qué es esto?

Claude Cockpit es un dashboard local de un solo usuario para orquestar instancias del Claude Code CLI. No es un servidor multi-tenant ni tiene autenticación compleja — arranca con pnpm dev y listo.

La idea central es: tú defines proyectos (rutas a repos locales), agentes (con su prompt, modelo y skills) y tareas en un kanban. Cuando arrastras una tarea a "En progreso" o pulsas "Ejecutar ahora", el cockpit pide confirmación —spawnear un agente cuesta dinero y un arrastre torpe no puede costarlo— y entonces lanza un proceso claude CLI que trabaja de forma autónoma sobre un workspace aislado: un git worktree si el proyecto es un repo, una copia si no.

Frontend

Next.js 15 App Router en :3000. Kanban con drag&drop, editor de agentes, gestor de skills y vista de ejecución en tiempo real.

Backend

Fastify 5 en :3001. REST API + SSE. Prisma con SQLite para persistencia local. p-queue para la cola de ejecuciones.

Proyectos

Un Project representa un repositorio local en disco. Es el contenedor de un kanban de tareas. Cada proyecto puede tener un CLAUDE.md asociado que se inyecta automáticamente en el workspace al ejecutar tareas.

Campos que se guardan en BD

CampoTipoDescripción
idcuidID único generado por Prisma
nameStringNombre del proyecto en la UI
descriptionString?Descripción opcional
repoPathStringRuta absoluta al repo o carpeta del proyecto — de aquí sale el workspace de cada run
workspaceStrategyStringworktree si repoPath es un repo Git, copy si no. Se detecta automáticamente al crear el proyecto
claudeMdIdString?FK al ClaudeMd del proyecto (nullable)

Importante: repoPath debe ser una ruta absoluta que exista en el sistema. Si es un repo Git, cada run trabaja en un git worktree con rama propia. Si no lo es, se copia el contenido excluyendo node_modules, .git, .next, dist y build.

La copia además no se lleva ficheros sensibles: .env (salvo .env.example y similares) ni bases de datos locales .db/.sqlite. Un workspace es un sandbox donde corre un agente autónomo que vuelca lo que lee a un log; copiar ahí el .env del proyecto sería entregarle las credenciales.

Ni tu carpeta de usuario ni la raíz del disco valen como repoPath: un git init ahí versionaría el perfil entero y cada run lo copiaría al workspace.

Agentes

Un Agent es una plantilla de ejecución. Define cómo se comporta el proceso de Claude: qué modelo usa, cuál es su rol, qué instrucciones de sistema tiene y qué skills puede usar.

Campos

CampoTipoDescripción
nameStringNombre visible en la UI
roleStringRol semántico: developer, reviewer, researcher… o cualquier string
modelStringID del modelo Claude: claude-opus-5, claude-sonnet-5, claude-haiku-4-5, claude-fable-5…
systemPromptStringInstrucciones de sistema del agente. Se inyectan al inicio del prompt que recibe el CLI
maxBudgetUsdFloat?Límite de gasto en USD por run. Si se supera, se mata el proceso. Solo salta mientras lleguen eventos de tokens: una run muda no la para nadie (para eso está RUN_TIMEOUT_MS)
allowedToolsString?Array JSON de herramientas del CLI que puede usar. null = sin restricción. Acepta patrones: Bash(git *)
disallowedToolsString?Array JSON de herramientas prohibidas. Es lo que permite "todo menos Bash" sin enumerar el resto
skillsAgentSkill[]Relación muchos-a-muchos con Skills habilitadas para este agente

Dónde se guarda: en la base de datos SQLite (apps/api/prisma/dev.db). La relación agente↔skill se guarda en la tabla AgentSkill con (agentId, skillId) como PK compuesta.

Un agente sin listas de herramientas puede ejecutar bash arbitrario dentro de su workspace, que es el comportamiento por defecto. Para un revisor o un documentador, allowedTools = ["Read","Glob","Grep"] basta.

Cuidado con el matiz: --allowedTools con la lista vacía no significa "todas", significa "ninguna". Por eso una lista vacía se guarda como null y nunca llega a la línea de comandos.

Skills

Una Skill es un fichero SKILL.md en disco. La base de datos nunca guarda el contenido, solo la ruta y un hash SHA-256 para detectar cambios. Si el fichero se edita fuera de la app, el scanner lo detecta automáticamente.

Estructura de un SKILL.md

---
name: mi-skill
description: Explica qué hace esta skill
tags: [typescript, testing, docs]
---

# Contenido de la skill

Instrucciones en markdown que Claude Code leerá cuando ejecute una tarea
que requiera esta skill. Puede contener ejemplos de código, convenciones,
checklists, etc.

Cómo se indexan

Al arrancar la API, el Skills Scanner (apps/api/src/skills/scanner.ts) recorre recursivamente los directorios definidos en SKILLS_PATHS buscando ficheros llamados exactamente SKILL.md. Por cada uno:

  1. Parsea el frontmatter YAML con gray-matter
  2. Calcula un hash SHA-256 del contenido
  3. Hace un upsert en la tabla Skill (insert o update si ya existe)

Además, chokidar vigila esos directorios en tiempo real: si añades, editas o borras un SKILL.md, la base de datos se actualiza sin reiniciar la API.

Dónde busca las skills

Configurable en la variable de entorno SKILLS_PATHS (paths separados por coma). Por defecto busca en ./skills relativo al directorio de la API.

Scope de una skill

El scope se infiere de la ruta del fichero:

  • Si la ruta contiene /public/ → public
  • Cualquier otra ruta → user

Qué se guarda en la BD

CampoDescripción
nameDel frontmatter name:. Si falta, usa el nombre del directorio padre del SKILL.md
descriptionDel frontmatter description:
filePathRuta absoluta al SKILL.md en disco
contentHashSHA-256 del contenido — para detectar cambios
scopeInferido de la ruta: public o user
tagsArray JSON serializado como string: ["typescript","testing"]

Nota: El contenido del SKILL.md nunca se guarda en la BD. Si borras el fichero en disco y había agentes que lo tenían asignado, la relación AgentSkill queda huérfana hasta que se limpie manualmente o se ejecute un cleanup al arranque.

Tareas (Kanban)

Una Task es la unidad del kanban. Pertenece a un proyecto y puede tener un agente asignado. Los estados del kanban reflejan el ciclo de vida de la tarea.

Estados

todo in_progress review done blocked

Cuando una run termina con éxito (exit code 0), la tarea pasa automáticamente a review para que el humano la valide. Si la run falla o se cancela, la tarea vuelve a todo en vez de quedarse colgada en in_progress para siempre.

En los dos casos, la tarea solo se toca si sigue en in_progress: si la moviste a mano mientras la run corría, se respeta tu decisión.

blocked no lo pones tú: lo gestiona el cockpit según las dependencias. Al cumplirse la última, la tarea pasa a todo y espera — desbloquear no es lanzar.

Campos destacados

CampoDescripción
titleTítulo corto que aparece en la tarjeta del kanban
descriptionDescripción detallada. Se incluye en el prompt que recibe el agente
assignedAgentIdAgente que ejecutará la tarea. Necesario para poder lanzar una run
dependsOnArray JSON de IDs de otras tasks. Bloquea la ejecución: una dependencia se considera cumplida solo cuando está en done. Los ciclos se rechazan al guardar, y una dependencia borrada deja de contar
priority0 baja, 1 media, 2 alta. Es el puntito de color de la tarjeta
positionOrden dentro de la columna del kanban

TaskRuns (Ejecuciones)

Un TaskRun es una ejecución concreta de una Task por un Agente. Está separado de Task a propósito: permite reintentos y mantiene un historial completo de cada ejecución con sus tokens y costes.

Estados

queued running succeeded failed cancelled

Qué guarda un TaskRun

CampoDescripción
workspacePathRuta absoluta al workspace de esta run. Una continuación comparte el del padre
branchNameRama del worktree. null si la estrategia es copy
logPathRuta al fichero NDJSON con todos los eventos del proceso claude
inputTokensTokens de entrada acumulados
outputTokensTokens de salida acumulados
cacheReadTokensTokens leídos de prompt cache
cacheWriteTokensTokens de escritura de caché (cache_creation_input_tokens). Se facturan a 1.25x el input y suelen ser el componente dominante del coste
costUsdCoste en USD. Estimado por tarifa mientras corre; al terminar lo sobreescribe el total_cost_usd del evento result, que es autoritativo
pidPID del proceso claude — necesario para matar su árbol de procesos
resultSummaryResumen del resultado (si el agente lo entrega)
failureKindPor qué falló: rate_limit (sin cuota, esperando decisión), rate_limit_waiting (reintento programado al reset) o error
rateLimitResetAtCuándo vuelve a haber cuota, leído del mensaje del CLI
sessionIdsession_id que anuncia el CLI. Es lo que permite retomar la run con --resume en vez de empezar de cero
resumedFromIdRun cuya sesión continúa esta. Comparte su workspace y su rama
followUpPromptInstrucciones con las que se retomó. null en una run de primera vuelta

El workspace de una run que salió bien no se borra al terminar. Queda en disco para que puedas ver el diff y decidir si lo integras. Se limpia al pasar la tarea a done, y solo si su trabajo ya está integrado.

Una run failed o cancelled sí se limpia sola, con dos excepciones: las cortadas por falta de cuota (su workspace es a donde vuelve el reintento) y las continuaciones, que viven en el workspace del padre y no son quién para borrarlo.

Además hay un GC por edad (WORKSPACE_GC_DAYS) que nunca borra trabajo que no esté guardado en otro sitio: si hay cambios sin commitear, no toca nada; de un worktree con commits sin integrar borra la carpeta pero conserva la rama.

CLAUDE.md

Los documentos ClaudeMd son instrucciones persistentes para Claude Code en formato Markdown. Se editan desde la sección "CLAUDE.md" de la app con el editor Monaco.

Scopes

ScopeCuándo se usa
globalInstrucciones para todos los proyectos. Se inyectan en el workspace de todas las runs. Solo puede haber uno
projectInstrucciones de un proyecto. Se inyectan solo en las runs de ese proyecto, después del global para poder matizarlo

Ambos se escriben en {workspace}/CLAUDE.md antes de lanzar el CLI, de modo que Claude Code los lee siguiendo su convención estándar. Si el repo ya traía su propio CLAUDE.md no se machaca: lo del cockpit se anexa en un bloque marcado con <!-- claude-cockpit -->, y reinyectar lo reemplaza en vez de acumularlo.

El scope agent ya no existe. Nunca lo consumió nadie, y el systemPrompt del agente ya es el sitio de las instrucciones propias de un agente: dos sitios para lo mismo solo sirven para preguntarse cuál gana.

Scanner de Skills

El scanner (apps/api/src/skills/scanner.ts) se encarga de mantener la base de datos sincronizada con los ficheros SKILL.md del sistema de ficheros.

Al arrancar la API

  1. Llama a scanSkills() → recorre todos los paths de SKILLS_PATHS
  2. Para cada SKILL.md encontrado: parsea frontmatter, calcula hash, hace db.skill.upsert()
  3. Inicia watchSkills() → chokidar observa cambios en tiempo real

Eventos que maneja chokidar

EventoAcción
add (fichero nuevo)Upsert en BD
change (fichero modificado)Upsert en BD (actualiza hash, description, tags)
unlink (fichero borrado)db.skill.deleteMany({ where: { filePath } })

Si el frontmatter de un SKILL.md tiene errores de YAML, gray-matter lanza una excepción. El scanner la captura, la loguea con console.warn y continúa con el siguiente fichero. La API no cae.

Flujo de ejecución de una tarea

Esto es lo que ocurre en detalle cuando pulsas "Ejecutar ahora" en una tarea:

1
Frontend → POST /tasks/:id/run

El TaskDrawer llama a tasks.run(taskId). El backend recibe la petición en apps/api/src/routes/tasks.ts.

2
Crear TaskRun y encolar

Antes de nada, el guard de dependencias: si a la tarea le falta alguna por terminar, se rechaza con un 400 y no se encola nada — da igual en qué columna la hayas puesto.

Si pasa, se crea un registro TaskRun con status: "queued", la tarea pasa a in_progress y la run entra en la p-queue (concurrencia por defecto 2, cambiable en caliente desde la UI). Se devuelve el runId al frontend.

3
Frontend navega a /runs/:id

Con el runId recibido, el frontend navega a la vista de ejecución y el hook useRunStream abre una conexión SSE a /runs/:id/stream.

4
Worker toma la run → executor.executeTaskRun(runId)

Cuando hay slot libre en la queue, el worker llama al ejecutor con el runId. Se carga el run completo de BD incluyendo la tarea, el proyecto y el agente con sus skills.

5
Preparar workspace

Se crea el directorio WORKSPACES_ROOT/{taskId}/{runId}/. Según project.workspaceStrategy:

  • worktree → git worktree add -b cockpit/task-{id}/run-{id}. El agente trabaja en su propia rama y el diff sale gratis.
  • copy → copia recursiva ignorando node_modules, .git, .next, dist, build, y saltándose .env y bases de datos locales.

Si la run es una continuación, este paso se salta: hereda el workspace del padre, porque el CLI indexa las sesiones por el directorio en el que corrieron.

WORKSPACES_ROOT/
  {taskId}/
    {runId}/
      src/          ← copia del repo
      package.json
      .claude/
        skills/
          mi-skill/ → symlink al directorio del SKILL.md
      CLAUDE.md     ← inyectado si el proyecto tiene uno
6
Instalar skills como symlinks

Por cada skill habilitada en el agente, se crea un symlink en .claude/skills/{skill.name}/ apuntando al directorio del SKILL.md en disco. Claude Code los carga automáticamente.

7
Inyectar los CLAUDE.md del cockpit

Se escriben en {workspace}/CLAUDE.md, en orden: primero el de scope global si existe, después el del proyecto. Claude Code los lee al arrancar. Si el repo ya traía uno, se anexan al final en un bloque marcado en vez de sobreescribirlo.

8
Construir el prompt

El prompt que recibe el CLI es la concatenación de:

{agent.systemPrompt}

---
# Tu tarea asignada

**{task.title}**

{task.description}

---
Tienes disponibles estas skills: {skill1, skill2}.
Cárgalas desde .claude/skills/ cuando sean relevantes.

Trabaja sobre el workspace actual. Cuando termines, entrega
un resumen breve del trabajo hecho.
9
Spawn del proceso claude CLI

Se ejecuta el CLI con los flags necesarios:

claude \
  -p "{prompt}" \
  --output-format stream-json \
  --verbose \
  --model {agent.model} \
  --permission-mode acceptEdits \
  [--allowedTools {lista} --disallowedTools {lista}] \
  [--resume {sessionId del padre}]

Los dos últimos son condicionales: los de herramientas solo si el agente tiene listas, y --resume solo si la run continúa otra.

Cómo se mata depende del sistema: en Unix se lanza con detached: true y se mata el process group con kill(-pid, 'SIGTERM'); en Windows, sin detached y con taskkill /T /F. Como taskkill no deja señal, la run se marca como cancelada antes de matarla: si no, un cancelado sería indistinguible de un fallo real.

10
Parsear stream-json línea a línea

El stdout del proceso se procesa línea a línea con readline. Cada línea es un objeto JSON del protocolo de Claude Code:

  • Si contiene usage → acumula tokens (deduplicando por message.id: el CLI emite un evento por bloque de contenido, todos con el mismo consumo), calcula coste, emite evento SSE
  • El primer session_id que aparezca se guarda en la run: es lo que permitirá retomarla
  • Toda línea se escribe al log NDJSON (LOGS_ROOT/{runId}.ndjson)
  • Toda línea se emite al EventEmitter bus → llega al SSE del frontend
  • Una línea que no sea JSON no rompe nada: se trata como log plano

La primera línea del NDJSON no viene del CLI: la escribe el cockpit antes del spawn, con el modelo, los flags y el prompt entero. Sin ella, cuando una run sale rara no hay forma de ver qué se le pidió.

11
Exit del proceso → estado final

Cuando el proceso termina:

  • Cancelada por el usuario → cancelled + tarea vuelve a todo
  • exit code 0 y sin error en el result → succeeded + tarea a review
  • Sin cuota del plan → failed con failureKind: "rate_limit", que la UI trata aparte: puedes esperar al reset o tirar de la API key
  • Cualquier otro fallo → failed + tarea vuelve a todo
  • Superado RUN_TIMEOUT_MS → failed, no cancelled: nadie la canceló

El cierre espera tanto al exit del proceso como al cierre de stdout: el proceso puede salir antes de que readline haya emitido las últimas líneas, y el evento result va justo al final.

Se emite el status final por el SSE de la run, y por el canal board van un task_updated para que el kanban refresque y un run_finished para el aviso del navegador.

Workspace

Cada run trabaja sobre un espacio aislado: un git worktree con rama propia si el proyecto es un repo, una copia si no. Así las ejecuciones concurrentes no se interfieren entre sí, y en modo worktree el trabajo del agente sale con un git merge normal.

WORKSPACES_ROOT/              ← por defecto: apps/api/workspaces/
  {taskId}/
    {runId}/                  ← workspace de esta run concreta
      src/
      package.json
      ...                       ← worktree del repo, o copia sin node_modules/.git/.env
      .claude/
        skills/
          mi-skill/           ← symlink → /ruta/original/de/la/skill/
      CLAUDE.md               ← inyectado desde BD si existe

LOGS_ROOT/                    ← por defecto: apps/api/logs/
  {runId}.ndjson              ← una línea JSON por evento del proceso

El workspace persiste tras una ejecución con éxito para que puedas revisar el diff y decidir si lo integras, desde la pestaña "Diff" del visor de run.

Se limpia solo: al pasar la tarea a done (si su trabajo ya está integrado), al mergear o descartar desde la UI, y por el GC de WORKSPACES_ROOT pasados WORKSPACE_GC_DAYS. La regla que el GC nunca rompe: liberar disco no puede destruir trabajo que no esté guardado en ningún otro sitio.

SSE Streaming

La comunicación en tiempo real usa Server-Sent Events. El servidor emite eventos y el browser los recibe con EventSource. No hay WebSockets.

Endpoints SSE

EndpointQué emite
GET /runs/:id/streamTodos los eventos de una run concreta (logs, tokens, status)
GET /board/streamCambios en el kanban (task creada, actualizada, borrada), cambios de la cola y run_finished al terminar una run
GET /projects/:id/plan/streamProgreso del planificador mientras propone el backlog inicial de un proyecto nuevo

Tipos de eventos SSE de una run

// Cambio de estado
{ type: "status", status: "running" | "succeeded" | "failed" | "cancelled" }

// Actualización de tokens y coste
{ type: "tokens", input: number, output: number,
  cacheRead: number, cacheWrite: number, costUsd: number }

// Evento del stream-json del CLI, tal cual
{ type: "stream", data: unknown }

// Salida que no era JSON (stderr, o una línea partida)
{ type: "log", line: string }

El keepalive no es un evento JSON: es una línea de comentario SSE (: ping) cada 30 segundos. Sin ella, una run que pase minutos sin emitir nada haría que el navegador o cualquier proxy intermedio diera la conexión por muerta.

Los tipos exactos están en apps/api/src/bus.ts (RunEvent, BoardEvent, PlanEvent).

Arquitectura interna del bus

El executor emite eventos al EventEmitter bus (apps/api/src/bus.ts). Las rutas SSE se suscriben a ese bus y reenvían los eventos al cliente HTTP. Cuando el cliente desconecta, el listener se elimina.

Budget y cálculo de costes

Cada agente puede tener un maxBudgetUsd. El ejecutor acumula tokens y calcula el coste después de cada evento de usage; si se pasa del budget, mata el proceso.

Ojo con lo que no cubre: el guard solo salta mientras sigan llegando eventos de tokens. Una run que se queda muda no la para el budget — para eso está RUN_TIMEOUT_MS.

Precios por modelo (USD por millón de tokens)

ModeloInputOutputCache WriteCache Read
claude-fable-5$10$50$12.50$1.00
claude-opus-5, claude-opus-4-8$5$25$6.25$0.50
claude-sonnet-5, claude-sonnet-4-6$3$15$3.75$0.30
claude-haiku-4-5$1$5$1.25$0.10

cacheWrite = 1.25x input y cacheRead = 0.1x input, así que la tabla se deriva de dos números por modelo. Los IDs con sufijo de fecha (claude-haiku-4-5-20251001) mapean a su ID base.

Esta tabla es solo una estimación en vivo. El evento result del stream-json trae total_cost_usd, que es autoritativo y sobreescribe la estimación al terminar la run. La tabla importa mientras corre: es lo que ve el guard de presupuesto.

Un modelo que no esté en la tabla se cobra a la tarifa más cara, a propósito: así el guard sobreestima en lugar de dejar pasar gasto.

Los precios están en apps/api/src/runner/pricing.ts. Actualízalos si cambian en docs.anthropic.com.

Copias de seguridad

Todo el cockpit vive en un solo fichero SQLite: proyectos, agentes, tareas y el historial entero de tokens y coste. Si se corrompe, no hay de dónde sacarlo.

La API hace una copia al arrancar en BACKUPS_ROOT y conserva las BACKUP_KEEP últimas. Es lo primero que hace, antes que el reaper o el scanner: si algo de lo que viene después dejara la BD en mal estado, la copia es de justo antes. Y nunca tumba el arranque — quedarse sin copia es malo, no arrancar es peor.

Se usa VACUUM INTO y no un copyFile: produce un snapshot consistente aunque haya escrituras en marcha, y de paso compacta. Desde el dashboard hay un botón para bajarse una en cualquier momento (GET /backup), que se genera en un temporal y se borra al enviarla: descargar diez veces no debe barrer las automáticas.

Restaurar es manual, a propósito. Para la API, copia el fichero encima de apps/api/prisma/dev.db y vuelve a arrancar. No hay endpoint de restore: sobrescribir la base de datos viva desde una petición web es justo lo que no quieres tener a un clic de distancia.

Los workspaces y los logs NDJSON no entran en la copia: los primeros son desechables y los segundos crecen sin límite. Si quieres conservar los logs de una run concreta, están en LOGS_ROOT.
